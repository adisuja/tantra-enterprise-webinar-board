Design: Funnel Analytics inside Tantra

Status: DRAFT v0 for office hours. Written with the gstack method (/office-hours design doc, then /plan-ceo-review, /plan-design-review, /plan-eng-review). Premises and approaches below are proposals until Adi confirms them, one question at a time. Mode: Startup (a paid feature for existing Tantra customers). Stage: has paying customers. Branch: claude/keen-goldberg-t4lxw8. Reference build: card 91, https://dashboard.usetantra.com.

Problem Statement

A Tantra customer runs outreach (calendar invites, LinkedIn, WhatsApp, email), sends people to a webinar or a call, and sells. Today the numbers for that journey live in four places: the Tantra app (invites and RSVPs), the webinar tool (registrations and attendance), the Tantra CRM (messages, bookings, deals, payments) and the content engine (posts and reach). Nobody can answer "where do my people drop off, and what did each stage cost me" without stitching exports together. Tantra sells the outcome (booked calls and revenue) but shows only the first step (RSVPs).

Demand Evidence

  • Our own team needed it first: card 51 (weekly dashboard) sat at "Not started" while the 12 Nov webinar ran, and card 91 had to be built by hand from five sources.
  • The dashboard kit exists because a previous client paid for exactly this view on a different stack (GoHighLevel and WebinarGeek).
  • Still missing: a named Tantra customer who asked for it, or who would be upset if it disappeared. This is Q1 below.

Status Quo

  • Tantra app: /reports shows invites, RSVP yes/maybe/no and WebinarGeek registrations for one broadcast. No stage conversion, no cost, no revenue. /dashboard is switched off, and its funnel functions return placeholders (dashboard.service.ts:450-478).
  • Tantra CRM: has a funnel engine (trk_funnels, trk_funnel_entries), tracked links, revenue transactions, costs and attribution tables, and a Links report. No customer-facing funnel dashboard.
  • Customers: spreadsheets and screenshots, or nothing (to be confirmed in Q2).

Target User and Narrowest Wedge

  • User (proposed): the founder or head of growth at a 5 to 50 person B2B company running weekly webinars or call funnels through Tantra. Their job depends on booked calls per week and cost per booked call.
  • Wedge (proposed): one fixed funnel, Invited to RSVP to Registered to Attended to Booked to Won, built automatically from data Tantra already holds, with zero setup beyond picking the campaign tag. That is what card 91 does for our own webinar.

Constraints (from the code, file references in the scratch reports)

  1. Main app tenancy is one user per tenant: every query is keyed on userId; there are no orgs, workspaces or roles. The CRM has workspaces and members.
  2. The main app records no opens, clicks, deliveries or replies for invites. campaign.metrics.* are never written. RSVP counts freeze once an event starts.
  3. There is no server-side plan or feature gating; the front end check fails open.
  4. Dark mode is switched off in the main app (<html class="light">), and many components hard-code light colours.
  5. Webinar platforms differ by customer (WebinarGeek is integrated in the app; we use WebinarJam via webhooks into D1; others use Zoom).
  6. Security must be fixed before analytics is sold: JWT issuer trust (jwt.strategy.ts:38-75), the cross-tenant read on GET /campaigns/metrics (campaign.service.ts:3217), the unchecked GET /subscription/:clerkId, unenforced API key scopes, and a committed encryption key in start-with-encryption.ps1.

Premises (to confirm, one at a time)

  1. Customers will pay for stage-to-stage conversion and cost per stage, not more raw counts.
  2. Every stage can come from data Tantra already holds or receives by webhook, with no new tracking for v1.
  3. A fixed funnel template per funnel type (webinar, call) beats a custom funnel builder for v1.
  4. Honesty rules stay non-negotiable: unavailable is never shown as zero, people are counted once, immature sales are labelled "so far", sources that disagree are flagged.
  5. The feature is sold as a plan entitlement (for example Pro and Enterprise), not as a separate product.

Approaches Considered

APPROACH A: Report inside the main app (minimal viable) Summary: A new /reports/funnel endpoint in ReportsModule and a (protected)/funnel-analytics page reusing LeadFunnelChart. Stages from campaigns, RSVPs and WebinarGeek only. Effort: M (human ~2 weeks / CC ~1 day) Risk: Low Pros: ships fastest; uses the app's auth, billing and nav; no new service. Cons: stops at attendance (no bookings, deals, revenue, cost, messaging), because those live in the CRM; single-user tenancy only. Reuses: reports.service.ts:186-363, LeadFunnelChart, FunnelStatsCard, the /api/reports/* proxy pattern.

APPROACH B: Funnel engine in the CRM, surfaced in both products (ideal architecture) Summary: The CRM's existing funnel engine (trk_funnels, stage rules on events) becomes the system of record. The main app pushes invite and RSVP events into it, webinar platforms post into it, and the dashboard model from card 91 (the metric cell contract, session assignment, maturity, confidence, scoring) runs as a CRM service. The main app embeds the view for its users; CRM workspaces get it natively. Effort: L (human ~6 weeks / CC ~1 week) Risk: Medium (two products, identity linking between a Tantra user and a CRM workspace) Pros: covers the whole journey to cash; workspaces and roles already exist; one funnel definition serves every funnel type; matches what card 91 already proves. Cons: needs a user to workspace link and an event push from the main app; the CRM shares D1's quota with its crons, so rollups are needed. Reuses: CRM trk_* tables and funnel engine, crm-worker tracking processor, card 91 builder (worker/src/funnels/webinar.js), the CRM's ws tenancy.

APPROACH C: Weekly funnel digest (lateral) Summary: No dashboard for v1. Every Monday each customer gets an email and WhatsApp summary: last week's funnel, the biggest drop, one recommended fix, built from the same model. Effort: S (human ~1 week / CC ~half a day after B's model exists) Risk: Low Pros: zero setup and zero new UI to learn; tests willingness to pay fast; easy to add to any plan. Cons: no drill-down; still needs the data plumbing from A or B; easy to ignore. Reuses: card 91 insights writer (worker/src/model.js), CRM sequences for delivery.

RECOMMENDATION: B, delivered in slices, with C as the first thing customers see. The full journey (to booked calls and cash) is the part customers cannot get anywhere else, and it only exists in the CRM. A stops before the money.

Recommended Approach (draft, pending approval)

Slice 1 (wedge): webinar funnel template in the CRM, fed by the main app's invites and RSVPs and by WebinarGeek, WebinarJam and Zoom webhooks; the card 91 model moved into a CRM service; weekly digest (C) on top. Slice 2: in-app view in the main app (shadcn and Recharts, dark mode switched on for this page), plan gating enforced in the backend. Slice 3: call funnel template (outreach to booked call to won) and custom stage rules.

Model contract (already proven in card 91)

Every figure is a cell: {v, k: LIVE|DERIVED|OPERATOR|MISSING, s: source, alts: [[source, value]], conflict, immature, floor}. A funnel model has sessions, views (all and per session), stages with conversion, breakdown, compare, trends, insights, sources health, confidence and score. The front end only displays it.

Open Questions (each will be asked on its own)

  1. Who is the first paying customer for this, by name? (Q1)
  2. What do they use today, and what does it cost them in hours? (Q2)
  3. Main app or CRM as the home of the funnel engine? (D1)
  4. Which plans include it, and is it an add-on price? (D2)
  5. Which webinar platforms must slice 1 support: WebinarGeek, WebinarJam, Zoom? (D3)
  6. Do customers need team access (several users on one funnel) in v1? This decides whether main app tenancy has to change. (D4)
  7. Should the security fixes in Constraint 6 ship before or with slice 1? (Recommendation: before.)

Success Criteria

  • Slice 1: three customer workspaces see their webinar funnel with no manual setup beyond picking a campaign tag; data confidence 70 or higher; numbers reconcile with source tools within 5%.
  • Commercial: 10 paying accounts on the plan that includes it within 60 days of launch, or a measured lift in upgrades.
  • Usage: weekly digest opened by 60% of recipients; dashboard visited weekly by 40% of accounts.

Distribution Plan

In-app (nav item next to Reports), the weekly digest, the pricing page, and our own webinar: the live Enterprise webinar dashboard is the demo.

Dependencies

Main app: security fixes, plan entitlements, an event push to the CRM (or a read API the CRM polls). CRM: rollups, a public read API per workspace, identity link to Tantra users. Content engine: a GET /api/tantra/metrics endpoint with date and label filters (proposed in the content engine report).

The Assignment

Before the next session: name three customers who run webinars or call funnels through Tantra, and ask each one "how do you know how many booked calls last week's outreach produced?" Write down their exact words.

Tantra Funnel Dashboard (card 91)

v2 is in progress in v2/ (kit design, many brands and funnels, integrations, themes, motion). Read ../../SESSION_HANDOFF_2026_11_14_DASHBOARD_V2.md first. The dashboard kit source is in references/dashboard-kit/. Everything below describes v1, which is what is live.

Live marketing analytics for Tantra funnels. The first funnel is the Tantra Enterprise Webinar; the funnel picker is built so more funnels can be added later.

Live: https://dashboard.usetantra.com

Sign in with the team password (Adi has it; it is a Worker secret, never in this repo). Data refreshes every 15 minutes, and the refresh button in the top bar rebuilds on demand.

Rules the numbers follow (from the dashboard kit)

  • Unavailable is shown as "n/a" and never as 0. A 0 is a measured zero.
  • People are counted once, by lowercased email. Attendance is distinct people with an attended webhook.
  • A registration belongs to the first session that has not ended when the person registered (the CRM's own rule). Attendance webhooks belong to the session that started at most 3 hours before.
  • Show-up uses aired sessions only. Someone WebinarJam reports as both attended and missed counts as attended.
  • Internal addresses (@usetantra.com, @jointantra.com, @sellwithtantra.com, @growthclub.org, test patterns), Adi's two test deals and test booking sources (localhost, live_test) are excluded everywhere.
  • Every figure carries a badge: Live, Calculated, Entered or Unavailable. When two sources disagree by more than 5% the figure says "Sources disagree" and both values show on hover.
  • Sales from a session are "so far" until it is 21 days old, and they never count toward a score before then.
  • Cost is a floor ("at least") until costs are entered in Settings. Revenue = won Enterprise deal value + RevOps OS buyers at $99 + Dodo payments.
  • If the registration database or the CRM fails on a refresh, the last good numbers stay on screen with a "Partial refresh" banner.
  • The page shows counts only. No name, email or phone number leaves the Worker.

Adding a funnel

  1. Add an entry to worker/src/funnels/registry.js: schedule, pipelines, link campaigns, booking pages, products, targets, stages.
  2. If it is a webinar funnel, the existing builder (worker/src/funnels/webinar.js) handles it. Another shape needs its own builder returning the same model contract.
  3. Deploy. The picker lists it.

Build, deploy, test

cd deliverables/91-funnel-dashboard/worker && npm install

CLOUDFLARE_API_TOKEN=proxy-injected npx wrangler deploy

From a Mac, run npx wrangler login once and then npx wrangler deploy. Secrets: DASH_PASSWORD, SESSION_SECRET, ENC_KEY (npx wrangler secret put <name>). Changing ENC_KEY means re-entering the keys in Settings; changing SESSION_SECRET signs everyone out.

Check the numbers against live data without deploying:

NODE_USE_ENV_PROXY=1 node test/live-model.mjs

Browser gate (every view at 1470 px and 390 px, light and dark, no errors, no horizontal overflow, pickers, tooltips and theme drawer):

NODE_PATH=$(npm root -g) node test/qa.cjs https://dashboard.usetantra.com <password file> <screenshot folder>

Known gaps

  • Calendar invites and RSVPs stay "Unavailable" until a Tantra app API key is saved in Settings.
  • Content engine numbers stay "Unavailable" until a token is saved. LinkedIn numbers need the engine batch ids listed in Settings.
  • Replay views are not tracked yet (no replay room). Call shows are only known when a deal is moved to Showed.
  • Cloudflare Zaraz (Google Analytics) and Web Analytics are switched on for the whole usetantra.com zone and inject themselves into this page. The page's security policy stops them sending data, but they should be switched off for dashboard.usetantra.com in the Cloudflare dashboard.
v2/ARCHITECTURE_V2.md

Funnel dashboard v2: architecture

Goal: the dashboard kit's design and model (the page at dashboard.fintechcirclepro.com), running on Cloudflare at dashboard.usetantra.com, for many brands, many funnels per brand, and any mix of software a client uses.

Layers

 Providers (read only)          Connectors                 Dataset store            Assembler                 Kit model             Page
 Instantly, HubSpot, Stripe ──▶ connectors/<id>.js  ──▶  D1 datasets table   ──▶ funnels/assemble.js ──▶ kit/build_model.js ──▶ kit UI (intel/command port)
 Tantra CRM, app, engine  ──▶   normalized datasets      per brand+connection      per funnel: kit bundle     same model.json       + brands, Funnels hub,
 webinar D1 (WebinarJam)        (connectors/_base.js)    (hourly, rate-limited)    (the kit's builder files)  contract as the kit    Integrations, themes, motion
  1. Connectors (worker/src/connectors/). One file per provider, the interface is documented at the top of _base.js. They return normalized datasets (DATASETS in _base.js): campaigns, touches, events, registrations, attendance, questions, bookings, deals, payments, contacts, messages, ad_daily, content_daily, link_clicks, web_daily. People are keyed by ctx.hash(email); no names, emails or phones are stored.
  2. Scheduler (worker/src/sync/). The Worker cron runs every 10 minutes. Each connection refreshes at most once per limits.refresh_minutes (60 by default), with at most limits.max_requests calls per refresh and per_second pacing. Connections are spread across the hour (a stable offset from the connection id), a 429 pushes the next run back, and an auth failure pauses the connection until the key is changed. Incremental cursors (since, cursor) keep later refreshes small.
  3. Dataset store (D1 tantra-dashboard): one row per (connection, dataset) holding the normalized JSON, chunked when large. Last good data is kept when a refresh fails.
  4. Assembler (worker/src/funnels/assemble.js). For one funnel: picks the connections assigned to each role (outreach, registration, attendance, booking, deals, payments, content, ads), builds the event list from the funnel template, assigns rows to events (registration: first event not yet ended; attendance: event window; bookings and payments: last event the person attended on or before, which is the kit's last-touch rule), and writes the kit's builder inputs (the "bundle").
  5. Kit model (worker/src/kit/build_model.js): a line-by-line port of intel/build_model.py, checked against the Python on the same inputs (test/parity/).
  6. Page: the kit's intel/command/* front end, served by the Worker, reading the model from /api/model. Added on top: brand switcher, Funnels tab (every funnel of the brand, each opening the same kit dashboard), Integrations (connect any provider; every empty section has a Connect button for the provider that would fill it), theme picker (light/dark plus colour and gradient themes), and the motion layer (the content kit's timeline engine: count-ups, wipes, draws, sheen) with an animated funnel recap post.

Brands, funnels, templates

  • brands(id, name, slug, colors, logo); connections(id, brand_id, provider, label, creds_enc, options, status, next_due, ...); funnels(id, brand_id, name, template, config, status).
  • Templates: webinar (events = sessions), call (events = weekly cohorts of booked calls), lead_magnet, challenge, launch. A template sets the event unit and its words ("webinar", "W12" or "week", "Wk 46"), the stages and which roles feed them.
