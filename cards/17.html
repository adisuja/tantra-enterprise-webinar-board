3. Registration

People register on our page (item 13). The page posts to the register Worker at integrations.register_worker_url (integration/register.mjs), which calls WebinarJam's /register endpoint for each person; that returns their unique live room link [H 15370151], and the Worker then posts webinar.registered with that join_url to the CRM. WebinarJam's own page stays unused, but the modules below still apply to API registrants.

What the Worker sends to /register: webinar_id, schedule (the next session that has not ended), first_name (or "there" if blank), email, last_name if given, and timezone_id when needed. WebinarJam requires timezone_id for registrants in Texas (2 = Mountain, 3 = Central) [H 15370151]. We only know the browser's time zone, so US Central zones (America/Chicago and its Indiana and North Dakota variants, America/Menominee) send 3 and US Mountain zones (America/Denver, America/Boise, America/Phoenix) send 2; everyone else sends none. Confirm in the WebinarJam dashboard with one test registration from a Central time zone browser.

Abuse guard on the Worker: it answers only the funnel domain's Origin (403 otherwise), checks a Cloudflare Turnstile token server-side, accepts only source: registration_page from the web, and caps every field length. Add a Cloudflare rate-limit rule as well (README step 5).

var tokenEl = form.querySelector('[name="cf-turnstile-response"]');

NO_API_KEY_PLAN.md

WebinarJam on the trial plan: how registration and data work without an API key (live 8 November 2026)

Event: "Tantra Enterprise Weekly", Thursday 12 November 2026, 11:00 AM, time zone Europe/London (fixed on 8 November: the session had been set to 11:00 AM US Eastern, which is 16:00 UK).

Into WebinarJam: the registration handoff

Our own registration popup on https://webinar.sellwithtantra.com/ stays exactly as designed. When someone submits it, the site Worker (card 46):

  1. saves the registration in D1 first, so nobody is lost;
  2. registers the person in WebinarJam with the same request WebinarJam's own registration form sends (it reads the form page for the session, CSRF token, honeypot value and time zone, then posts the details);
  3. reads the person's personal live-room link from WebinarJam's thank-you page and returns it, so the confirmation page shows it.

WebinarJam then sends its own confirmation and reminder emails. Typical time: 3 to 4.5 seconds. Failures are recorded in D1 (wj_status, wj_error) and retried every 5 minutes, up to 6 times. This is WebinarJam's form endpoint, not a published API: if WebinarJam changes its form, the retries fail visibly in D1 and the registration itself is never lost.

Why not WebinarJam's embedded form: it loads in an iframe from WebinarJam's domain, so our design cannot be applied inside it beyond four templates and colours.

Out of WebinarJam: the Custom Webhook

Profile, Integrations, Autoresponder, Custom Webhook: base URL https://webinar.sellwithtantra.com/api/wj , Bearer token (in ~/.config/tantra/keys/webinar-site.env). Rules on the event:

WebinarJam trigger Path
They register /registered
They attend the live webinar /attended
They miss the live webinar /missed
They attend the webinar replay /replay
They leave before 0 hr 25 min /left-early

Payload (confirmed on a test registration): trigger, lead (first and last name, email, phone country code and number, custom fields), links (personal live_room, personal replay_room, unsubscribe), webinar (id, name). Every call is stored in the D1 table wj_events. This feeds the WhatsApp messages (card 42), the post-session bonus and replay messages, and the CRM sync (card 41).

  • Webhook: the "register" trigger reached /api/wj/registered within seconds with the payload above.
