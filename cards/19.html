6. Webhook to the CRM

Event type, Webhooks tab, New webhook.

Field Value
Subscriber URL {integrations.crm_webhook_url}?k={SHARED_SECRET} (the Apps Script web app URL ending in /exec, plus the secret shown by Tantra CRM, Set up)
Enable webhook On
Event triggers Booking Created, Booking Rescheduled, Booking Cancelled, Booking No-Show Updated, Meeting Ended
Secret Leave empty. Apps Script cannot read request headers, so Cal.com's signature header cannot be checked; the ?k= secret protects the URL instead
Payload template Default

Meeting Ended fires at the end time of every confirmed booking, whatever the location, and its payload is flat (no payload wrapper). The CRM uses it as a backstop: if no outcome is logged by then, the closer gets an outcome task. Booking No-Show Updated with noShow: false (an unmark) is logged and raises a closer task; it never changes the stage.

Apps Script answers a POST with a redirect after it has run. The CRM row is written either way; if Cal.com shows the delivery as failed, check the Events tab before retrying.

Payload mapping (Cal.com to CRM_CONTRACT)

Cal.com trigger Contract event Cal.com field Contract field
BOOKING_CREATED booking.created payload.attendees[0].email email (lowercased)
payload.uid data.cal_uid
payload.startTime data.start
payload.organizer.email, matched to the Closers table on the Lists tab data.closer (Conor or Scott)
payload.responses.<identifier>.value for revenue_band, invest_12m, main_channel, bottleneck, signoff data.answers{}
payload.responses.name, payload.attendees[0].name data.first_name, data.last_name
payload.responses.whatsapp, payload.responses.company data.whatsapp, data.company
payload.attendees[0].timeZone data.timezone (drives WhatsApp hours and the time shown to the lead)
payload.metadata.videoCallUrl data.join_link
BOOKING_RESCHEDULED booking.rescheduled payload.uid, payload.startTime data.cal_uid, data.start
BOOKING_CANCELLED booking.cancelled payload.cancellationReason data.reason
BOOKING_NO_SHOW_UPDATED call.no_show (one per attendee with noShow: true) payload.attendees[].email, payload.bookingUid email, data.cal_uid
MEETING_ENDED (flat payload) none in the contract attendees[0].email at the top level Outcome task for the closer if no outcome is logged yet
BOOKING_NO_SHOW_UPDATED, noShow: false none in the contract payload.attendees[].email Logged; closer task to check the call and log the outcome

Bookings whose payload.type is proposal-review (the calcom_call2_slug setting) are Call 2: see section 8. Bookings of any other type than these two (calcom_event_slug, calcom_call2_slug) are logged and ignored. Duplicate deliveries are dropped for 6 hours.

Unverified: these field names come from Cal.com's webhook documentation and the recorded payloads used in the workshop project, not from a live delivery of this event type. The adapter reads several fallbacks (userFieldsResponses, videoCallData.url, location). The first test booking in section 7 proves them.

Webhook (the Call 2 Marker)

Event type, Webhooks tab, New webhook, the same fields as section 6 (same Subscriber URL with ?k=, same five triggers, secret empty, default payload).

The marker is the event type slug. Every Cal.com payload carries payload.type (for MEETING_ENDED, type at the top level). When it equals proposal-review (Lists setting calcom_call2_slug), the CRM reads the booking as Call 2 and posts the contract event with data.call: 2:

Cal.com trigger Contract event What the CRM does
BOOKING_CREATED, type proposal-review booking.created, call: 2 Sets call2_date, call2_status Booked, call2_cal_uid, call2_join_link. The deal stays in 5 Proposal Sent (a deal in Showed, Follow-Up or Nurture moves to 5), never back to Call Booked. Seq. D stops, Seq. R starts, closer alert
BOOKING_RESCHEDULED, type proposal-review booking.rescheduled, call: 2 New Call 2 time, call2_status Rescheduled, Seq. R restarts
BOOKING_CANCELLED, type proposal-review booking.cancelled, call: 2 call2_status cleared, note on the row, Seq. RC. The deal stays in 5 Proposal Sent
BOOKING_NO_SHOW_UPDATED call.no_show Matched to Call 2 by the booking uid (call2_cal_uid): call2_status No-Show, Seq. RN
MEETING_ENDED, type proposal-review none Outcome task if Call 2 is still Booked or Rescheduled

The deal keeps its Call 1 closer even if the booking comes in on the other closer's link; the alert names both.
